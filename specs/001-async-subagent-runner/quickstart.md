# Quickstart Validation: Async Sub-agent Runner

## Prerequisites

- Open the TaskSync workspace in VS Code.
- For live tests only, explicitly enable the suite, authenticate OpenCode's provider, and configure an allowed cheaper model through environment/runtime test configuration. Do not place credentials or a credential-bearing config in source.
- Build the touched TypeScript packages using their existing project commands.
- Use a bounded Explorer request with explicit stop and evidence contracts that requires at least one streamed response.
- Use `realpath /Users/machs/PycharmProjects/TaskSync` as the server/reuse key and the plan-approved immutable base revision `2eaeba0d3f45e8ee191f6b802cc30bbda1df3941`. If the checkout differs, report the mismatch; do not substitute dispatch-time `HEAD`.

## Validation Scenarios

1. Execute the exact shared-server spike in [plan.md](plan.md). Expected evidence: immediate non-terminal handle, one server process shared by all workspaces, exact viewer session, streamed update, matching worker/run/session IDs, and terminal `step_finish` metrics.
2. Start two bounded workers in the same workspace and select a compatible idle worker. Then submit behind a worker whose estimated queue wait exceeds 120 seconds. Expected: same profile can have multiple workers; the first selection reuses only if eligible; the second creates an ad hoc worker; server count remains one.
3. Reload the extension while a server remains live. Expected: registry reconnects and preserves the exact session link. Prune an inactive empty-queue worker. Expected: an archive record is retained; active or queued workers cannot be pruned.
4. Exercise `/tmp` read/write, a safe command, and an approval-requiring action. Expected: first two proceed under allow-all; the third is approved only in OpenCode and appears in AskAway as a notification without approval controls or secrets.
5. Simulate cache expiration and context `300001`. Expected: each worker becomes visibly `RETIRED` with reason, cannot be reused, and requires a fresh submission.
6. Submit two bounded runs to the same eligible worker. Expected: historical/cached input context remains visible, each fresh `runId` starts elapsed time and cost at zero, and no transcript compaction or indefinite-retention behavior is required.
7. Verify lifecycle and cost persistence. Expected: current-workspace records contain worker/run/adapter-session and dispatching-main-agent-turn IDs; the existing expandable trace retains per-run time, cost, input, and output; all worker usage is attributed to the dispatching turn.
8. Enumerate the public control operations. Expected: exactly the eight operations in [contracts/worker-runtime.md](contracts/worker-runtime.md); no `worker_ask`, `worker_respond`, central sender/recipient routing, or messaging implementation exists.
9. Assemble a selected-task Cloud Worker Packet from the schema in [plan.md](plan.md). Expected: every required field is concrete and self-contained, the approved immutable base revision is unchanged, and dispatch rejects missing fields, `TBD`, placeholder prose, unresolved decisions, or secrets.
10. Configure one mode/profile with an adapter/platform, at least two allowed model options, and at least two allowed thinking budget/tier options. Dispatch each allowed selection. Expected: the returned handle, persisted `WorkerRun`, lifecycle records, and expandable trace show the same effective adapter/model/thinking values selected by the user or orchestrator.
11. Request a model or thinking option that is not allowed, then make an allowed configured option unavailable at runtime. Expected: each request returns an explicit unavailable/ineligible result; no other primary agent, adapter, model, or thinking option runs. Change the selected model or thinking option on a subsequent run. Expected: the run is marked as a cache boundary and does not claim continuity with the previous selection's cache.
12. Run deterministic orchestrator policy tests. Expected: implementation-code read/search/navigation/edit/file-mutation/build/execution tools are denied, while planning, worker control, skill/memory, internet, SharePoint, architecture MCP, and evidence-verification capability classes are allowed.
13. Feed a fixed bounded task graph and fixed worker availability into the no-network router twice. Expected: both runs select the same ready node, worker mode/profile, adapter, model, and thinking budget; cycles, graph-limit overflow, and out-of-profile selections are rejected.
14. Validate Cloud Worker Packets with complete and incomplete fixtures. Expected: a complete packet includes orchestrator turn, graph/node, mode/profile, adapter/model/thinking, self-contained context, objective, constraints, acceptance/evidence, stop policy, and applicable live budget. Missing fields, placeholders, credentials, mutable inaccessible references, or mismatched turn attribution are rejected.
15. Present a node with insufficient evidence. Expected: it becomes `EVIDENCE_INSUFFICIENT`, a bounded research/data-collection node is routed, synthesized findings become explicit downstream context, and the original node is not accepted until the orchestrator independently verifies mapped evidence. Unbounded expansion stops.
16. Run the live OpenCode suite separately with one worker/run and configured timeout and maximum cost. Expected: missing enablement, runtime, auth, profile, or cheaper-model availability causes an explicit pre-dispatch skip; any failure after dispatch fails. A passing run exposes real provider `step_finish` input/output/reasoning/cache/cost fields, derives budget totals from those fields, and attributes them to the dispatching turn. Timeout or cost breach cancels without fallback and records `STOPPED_BUDGET`.
17. Reuse an eligible worker after a completed run. Expected: historical input remains visible, while the new run's elapsed and cost begin at zero and subsequent provider usage remains attributed to the new run's dispatching main-agent turn.
18. Verify durable capture routing with representative outcomes. Expected: repeatable procedures map to skills, concise verified facts to memory, user-approved durable decisions to ADR candidates, and operational/product behavior to documentation; implementation details alone cannot create an ADR.

## Test Evidence

Implement behavior-level tests against the operation and UI contracts in [contracts/worker-runtime.md](contracts/worker-runtime.md) and state rules in [data-model.md](data-model.md). The default suite is deterministic and no-network. Live tests are opt-in, bounded, serial, and use external provider configuration. Tests must assert caller-visible handles, effective selections, explicit unavailable/ineligible results without fallback, cache-boundary behavior, state/metrics, exact live-session opening, terminal provider evidence/failure, independent acceptance, attribution, and retirement behavior rather than private bridge implementation details.
